## 3. v0.3.0 主要实现

### 3.1 Hugging Face RMSNorm 适配器

核心文件：

```text
integrations/huggingface_rmsnorm.py
integrations/__init__.py
```

已实现：

- `HuggingFaceTritonRMSNorm`
- `from_huggingface_module`
- `replace_huggingface_rmsnorm_modules`
- LlamaRMSNorm 自动递归替换
- Qwen2RMSNorm 自动递归替换
- 保留原始 `Parameter` 对象
- 保持 `state_dict` 键和值一致
- CUDA `inference_mode` 下使用 Triton RMSNorm
- CPU、训练模式或不支持条件下回退 Hugging Face 风格 PyTorch 实现

### 3.2 设计原则

该适配器不是重新创建一套独立模型权重，而是将 Hugging Face 模型中的 RMSNorm 模块替换为兼容接口的 Triton 适配器。

替换后需要保证：

1. 原始参数对象不被破坏；
2. `state_dict` 键保持不变；
3. 保存和加载模型时兼容原始 Hugging Face 权重结构；
4. CUDA 推理时能够进入 Triton 快速路径；
5. CPU 或训练模式下能够安全回退；
6. 不支持的输入条件不会导致错误使用 Triton Kernel。

## 11. Transformers 5.14.1 KV Cache API 验证

LlamaForCausalLM 和 Qwen2ForCausalLM 的 `forward` 均使用：

```text
past_key_values: transformers.cache_utils.Cache | None
```

实际验证确认：

- Prefill 自动返回 `DynamicCache`
- Decode 返回与输入相同的缓存对象
- 缓存由模型原地更新
- 输入一个新 Token 后缓存长度增加 1
- Llama 和 Qwen2 接口行为一致
- 旧版元组式 KV Cache 接口不能直接套用
- `DynamicCache.crop(max_length)` 可稳定裁剪缓存

连续 Decode 与每一步完整序列前向对比：

- Llama 最大误差约 0.000030518
- Qwen2 本次误差为 0

因此当前 KV Cache 使用方式正确。

## 12. 真实 KV Cache Decode Benchmark

Benchmark 文件：

```text
benchmarks/benchmark_huggingface_kv_cache_decode.py
```

### 12.1 实验流程

1. 随机初始化紧凑 Llama 或 Qwen2；
2. Hugging Face 原始模型与 Triton 模型使用完全相同的参数；
3. 先执行一次 Prefill；
4. 使用 `use_cache=True` 生成独立 `DynamicCache`；
5. 后续每次只输入一个新 Token；
6. 正确传递 `past_key_values`；
7. 每个 Provider 使用独立缓存；
8. 每次 Decode 后使用 `DynamicCache.crop(prefill_length)` 恢复固定上下文；
9. 缓存裁剪位于 CUDA Event 计时区间之外；
10. 模型构造、权重复制、模块替换和首次 Triton 编译不计入稳态延迟；
11. Provider 顺序进行轮换；
12. 不下载外部权重。

### 12.2 正式实验配置

| 项目 | 配置 |
|---|---|
| 模型 | Llama、Qwen2 |
| 精度 | FP16、BF16 |
| batch size | 1 |
| Prefill 长度 | 32、128、512 |
| 正式轮数 | 3 |
| 每场景预热 | 20 次 |
| 每场景测量 | 100 次 |
| 计时方式 | CUDA Event |
| Decode 输入 | 每次 1 Token |

三轮正式实验共：

- 72 条 Provider 记录
- 12 个模型/精度/上下文组合
- 36 组成对 Provider 比较

所有记录均为：

```text
status=ok
```

### 12.3 Triton 调用次数

每个紧凑模型包含 9 个 RMSNorm。

验证结果：

- Prefill 实际调用 Triton RMSNorm：9 次
- 每个 Decode Token 实际调用 Triton RMSNorm：9 次

说明真实 Decode 确实进入 Triton RMSNorm 路径。

### 12.4 正确性

三轮最大 logits 绝对误差：

| 精度 | 最大绝对误差 |
|---|---:|
| FP16 | 0.001953125 |
| BF16 | 0.015625 |

所有正确性检查均通过。

### 12.5 三轮总体性能结果

| 指标 | Hugging Face | Triton RMSNorm |
|---|---:|---:|
| Decode P50 平均延迟 | 约 1.0921 ms | 约 1.0963 ms |
| Decode 平均吞吐 | 约 916.03 tokens/s | 约 912.44 tokens/s |

成对平均加速比：

| 阶段 | 三轮成对平均加速比 |
|---|---:|
| Prefill | 0.9959× |
| 单 Token Decode | 0.9962× |

最终结论：

> 在随机初始化的紧凑 Llama/Qwen2 模型、batch size 1、Prefill 长度 32/128/512、FP16/BF16 和真实 DynamicCache 单 Token Decode 条件下，替换 Triton RMSNorm 后的端到端 Decode 性能与 Hugging Face 原始模型基本持平，三轮成对平均加速比约为 0.9962×。

### 12.6 P95 偶发抖动

第 3 轮：

```text
Qwen2 + BF16 + prefill_length=512
```

Triton Prefill 出现一次孤立的 P95 抖动：

| 指标 | 结果 |
|---|---:|
| Prefill P50 | 1.231872 ms |
| Prefill P95 | 2.574848 ms |
| P95/P50 | 2.090 |

前两轮对应 P95/P50 约为：

- 1.024
- 1.027

同一场景的 Decode 延迟正常，第 3 轮 Hugging Face Prefill 也正常。

因此：

- 原始数据保留
- 不删除或篡改异常值
- 不重跑整组三轮实验
- 不将其解释为稳定尾延迟退化
- 正式性能结论主要依据三轮成对 P50

专项报告：


## 15. 综合结论

v0.3.0 已经完成从独立 Triton RMSNorm Kernel 到 Hugging Face 模型集成的完整验证闭环：

```text
Hugging Face 模块替换
        ↓
参数和 state_dict 兼容性验证
        ↓
CPU fallback 与 CUDA Triton 路径验证
        ↓
Llama/Qwen2 整模型正确性验证
        ↓
模块级三轮 Benchmark
        ↓
hidden size 512 对齐实验
        ↓
输入布局诊断
        ↓
PyTorch Profiler 归因
        ↓
真实 KV Cache Decode 三轮 Benchmark
```

核心结论：

1. Triton RMSNorm 可以正确集成到 Hugging Face Llama 和 Qwen2；
2. 模块级 RMSNorm 性能获得约 2.75×～4.67× 的平均加速；
3. hidden size 512 时模块级加速仍然明显；
4. 输入布局不存在额外 `contiguous()` 复制问题；
5. Profiler 证明 RMSNorm Kernel 数和累计时间显著下降；
6. 真实 KV Cache Decode 下端到端性能与 Hugging Face 原始模型基本持平；
7. 模块级 Kernel 加速不能直接等同于整模型端到端加速；
8. v0.3.0 的主要价值不仅是展示加速结果，也在于给出完整、可复现、可归因的性能分析。

严谨的最终表述：

> LLM-KernelLab v0.3.0 成功将 Triton RMSNorm 集成到 Hugging Face Llama 和 Qwen2 模型，在保持参数结构、state_dict 和模型正确性的前提下，显著减少 RMSNorm Kernel 数量和累计执行时间。模块级 Benchmark 获得明显加速，但在当前随机初始化紧凑模型、batch size 1 和真实 KV Cache 单 Token Decode 场景中，端到端性能与 Hugging Face 原始模型基本持平。
