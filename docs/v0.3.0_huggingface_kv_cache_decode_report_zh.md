# v0.3.0 Hugging Face 真实 KV Cache Decode Benchmark 报告

## 1. 实验目的

本实验用于评估在 Hugging Face Llama 和 Qwen2 因果语言模型中，将原始 RMSNorm 替换为 LLM-KernelLab 的 Triton RMSNorm 后，对真实 KV Cache 单 Token Decode 性能的影响。

此前的 `single_token_no_cache` 场景只是无 KV Cache 的单 Token 前向，不能代表真实自回归 Decode。本实验补充了完整的 Prefill、`past_key_values` 传递和逐 Token Decode 流程。

## 2. 实验实现

Benchmark 脚本：

```text
benchmarks/benchmark_huggingface_kv_cache_decode.py
```

实验流程如下：

1. 随机初始化紧凑 Llama 或 Qwen2 模型，不下载预训练权重；
2. 为 Hugging Face 原始模型和 Triton RMSNorm 模型复制完全相同的参数；
3. 先执行一次 Prefill，并使用 `use_cache=True` 生成独立的 `DynamicCache`；
4. Decode 时每次只输入一个新 Token，并传入对应模型自己的 `past_key_values`；
5. 每次 Decode 后使用 `DynamicCache.crop(prefill_length)` 将缓存恢复到固定上下文长度；
6. 缓存裁剪位于 CUDA Event 计时区间之外；
7. 模型构造、权重复制、RMSNorm 替换和首次 Triton 编译均不计入稳态延迟；
8. Provider 顺序根据模型、精度、上下文长度和 `run_index` 进行轮换，以降低顺序偏差；
9. 每个测试场景预热 20 次，正式测量 100 次；
10. 共执行三轮正式实验。

## 5. KV Cache API 验证

Transformers 5.14.1 中，Llama 和 Qwen2 的 `past_key_values` 均使用 `transformers.cache_utils.Cache` 接口。

实际验证结果：

- Prefill 自动返回 `DynamicCache`；
- Decode 返回与输入相同的缓存对象；
- 缓存由模型原地更新；
- 输入一个新 Token 后，缓存长度增加 1；
- `DynamicCache.crop()` 能在 Decode 后将缓存稳定裁剪回指定长度；
- 重复执行“Decode 后裁剪”时，logits 保持一致。

因此，本实验为真实 KV Cache Decode，而不是无缓存单 Token 前向。

## 6. 正确性验证

三轮正式实验共包含 72 条 Provider 记录，全部为 `status=ok`。

每个紧凑模型包含 9 个 RMSNorm：

- Prefill 中实际调用 9 次 Triton RMSNorm；
- 每个 Decode Token 中实际调用 9 次 Triton RMSNorm；
- Llama 和 Qwen2 的缓存长度始终与预期一致。

最大 logits 误差：

| 精度 | 三轮最大绝对误差 |
|---|---:|
| FP16 | 0.001953125 |
| BF16 | 0.015625000 |

这些误差处于当前精度和整模型累积计算可接受范围内，所有正确性检查均通过。

## 8. 总体结果

三轮 12 个场景的总体平均结果：

| 指标 | Hugging Face | Triton RMSNorm |
|---|---:|---:|
| Decode P50 平均延迟 | 1.092118 ms | 1.096257 ms |
| Decode 平均吞吐 | 916.03 tokens/s | 912.44 tokens/s |

成对平均加速比：

| 阶段 | 平均加速比 |
|---|---:|
| Prefill | 0.9959× |
| 单 Token Decode | 0.9962× |

按成对平均值计算，Triton RMSNorm 模型在真实单 Token Decode 中平均约慢 `0.38%`。该差异小于 1%，可以视为端到端性能基本持平，而不是稳定加速或稳定退化。

## 9. P95 异常说明

在第 3 轮 `Qwen2 + BF16 + prefill_length=512` 场景中，Triton Prefill 出现一次孤立的 P95 抖动：

- Prefill P50：1.231872 ms
- Prefill P95：2.574848 ms
- P95/P50：2.090

同一场景的前两轮 P95/P50 分别约为 1.024 和 1.027，第 3 轮 Hugging Face Prefill 以及两边 Decode 延迟也保持正常。因此该值被保留在原始结果中，但不解释为稳定的尾延迟退化。正式性能结论主要依据三轮成对 P50。

## 10. 结论

本实验表明：

1. LLM-KernelLab 的 Hugging Face Triton RMSNorm 适配器能够正确用于 Llama 和 Qwen2 的真实 KV Cache Decode；
2. Prefill 和每个 Decode Token 都确实经过 9 次 Triton RMSNorm；
3. FP16 和 BF16 正确性均通过；
4. 三轮实验中，真实 Decode 的端到端延迟与 Hugging Face 原始模型基本持平；
5. Triton RMSNorm 虽然能够显著减少单独 RMSNorm 模块的 Kernel 数量和 Kernel 时间，但在当前紧凑模型、batch size 1、单 Token Decode 场景中，端到端延迟仍主要受注意力、线性层、框架调度和 Kernel Launch 间隙等其他部分影响；
6. 因此，不能将模块级 RMSNorm 加速直接等同于整模型 Decode 加速。

严谨表述应为：

> 在随机初始化的紧凑 Llama/Qwen2 模型、batch size 1、Prefill 长度 32/128/512、FP16/BF16 和真实 DynamicCache 单 Token Decode 条件下，替换 Triton RMSNorm 后的三轮端到端 Decode 性能与 Hugging Face 原始模型基本持平，成对平均加速比约为 0.9962×。
